** Degree of Associations : Aggregation and Composition
https://www.youtube.com/watch?v=gxyUK14VU4Q&list=PLJ17ef_rBpHVSfPoF7ZqCTOKLiqUfdHco&index=100

*Definiton with Example*: In a Library (Container class) there are books(contained) and students(contained). Library and Books has strong relationship. If Library is closed Books wont be available (Composition) . For Students relationship is weaker. If library is closed Students can get books from somewhere else (Aggregation).

Example 2: A Car (Container) has an Engine(Contained). Car needs a engine to run but Engine can run by itself too. This is Aggregation. This is a weak association because engine can function independently.

*** Aggregation
- It is a weak association between 2 entities.
- If we close the container object, the contained object may not be closed with container.
- Lifetime of contained object is does not depend upon the life time of the container object.

*** Composition
- It is a strong association between 2 entities.
- If we close the container object, then the contained object will also be closed with container.
- Lifetime of contained object is totally depend on the life time of the container object.

* TypeCasting
Type casting is simple converting from one form to another form.
** Class Level Type Casting
*** Upcasting
Converting subclass type to super class type. Child object will be converted/casted to parent object.
- Upcasting is a way to force usage of overwritten methods in child class. If same method is defined in parent and child class, child class method will be used. If a method exist only in parent class, you will be using parent class methods. If we try to use a method that only exist in child class and doesn't exist in parent class, we will get an error.

Upcasting is: =Parent one = new Child();=

**** Java Type Casting, Inheritance, and Method Resolution Notes

***** Method Resolution and Type Casting

- Java is statically typed:
  - The **reference type** determines which methods can be called at **compile time**.
  - The **actual object type** determines which method is **executed at runtime** (for overridden methods).

- Example:
  #+begin_src java
  class Parent {
      void show() { System.out.println("Parent"); }
  }

  class Child extends Parent {
      void show() { System.out.println("Child"); }
      void specific() { System.out.println("Specific to child"); }
  }

  Parent p = new Child();
  p.show();           // Output: "Child"
  p.specific();       // ❌ Compile-time error
  ((Child) p).specific(); // ✅ Works after downcasting
  #+end_src

- Why does `p.specific()` not work?
  - Because the reference type `Parent` does not know about `specific()`.
  - Method resolution is based on the reference type at compile time.

***** Why Type Cast at All?

- If you already have a `Child` reference, type casting is not needed.
- But in real-world code, you often deal with **superclass or interface references**.
- Upcasting is a way to force usage of overwritten methods in child class. If same method is defined in parent and child class, child class method will be used. If a method exist only in parent class, you will be using parent class methods. If we try to use a method that only exist in child class and doesn't exist in parent class, we will get an error.

****** When Type Casting Is Useful

1. **Accessing subclass-specific methods**
   #+begin_src java
   Parent p = new Child();
   ((Child) p).specific(); // Access Child-specific method
   #+end_src

2. **Working with interfaces**
   #+begin_src java
   interface Animal { void makeSound(); }

   class Dog implements Animal {
       public void makeSound() {}
       public void fetch() {}
   }

   Animal a = new Dog();
   ((Dog) a).fetch(); // Cast needed to call Dog-specific method
   #+end_src

3. **Collections or framework code**
   #+begin_src java
   List<Animal> animals = new ArrayList<>();
   animals.add(new Dog());
   animals.add(new Cat());

   for (Animal a : animals) {
       if (a instanceof Dog) {
           ((Dog) a).fetch();
       }
   }
   #+end_src

4. **Polymorphic methods**
   #+begin_src java
   void handle(Animal a) {
       a.makeSound();
       if (a instanceof Dog) {
           ((Dog) a).fetch();
       }
   }
   #+end_src

****** When Type Casting Is Not Needed

- If you're directly working with a `Child` object:
  #+begin_src java
  Child c = new Child();
  c.specific(); // No casting needed
  #+end_src

****** Summary Table

| Situation                                 | Use Child Directly? | Need Type Cast? | Why?                                 |
|-------------------------------------------+----------------------+-----------------+--------------------------------------|
| You control the code and use only `Child` | Yes                  | No              | Simpler                              |
| Using polymorphism with `Parent`/interface| No                   | Yes             | Need subclass-specific behavior      |
| Frameworks/Collections return base types  | No                   | Yes             | You don’t control return/reference   |

*** Downcasting
**** Java: instanceof and Downcasting

***** What is `instanceof`?

- `instanceof` is a type-checking operator in Java.
- Syntax:
  #+begin_src java
  objectRef instanceof ClassName
  #+end_src
- Returns `true` if the object is an instance of `ClassName` or its subclasses (or implements the interface).
- Returns `false` otherwise.
- Safe to use on `null` — returns `false` (does NOT throw an exception).

***** Why use `instanceof` with downcasting?

- Downcasting can throw a `ClassCastException` if the object is not of the expected type.
- `instanceof` allows you to check the type safely **before** performing the cast.

***** Safe Downcasting Pattern

#+begin_src java
Parent p = new Child();

if (p instanceof Child) {
    Child c = (Child) p;  // ✅ Safe downcast
    c.special(); //Assume special() doesn't exist in Parent. So now we can use it because we casted to Child class.
}
#+end_src

***** Example: How it works

#+begin_src java
class Parent {
    void greet() {
        System.out.println("Hello from Parent");
    }
}

class Child extends Parent {
    void play() {
        System.out.println("Playing in Child");
    }
}

Parent p = new Child();

if (p instanceof Child) {
    ((Child) p).play(); // ✅ Safe: Child method is accessible
} else {
    System.out.println("Not a Child");
}
#+end_src

***** Important Notes

- `instanceof` checks the **actual object type**, not just the reference type.
- Works across both class hierarchies and interfaces.

#+begin_src java
Object o = "hello";

if (o instanceof String) {
    System.out.println("It's a string!"); // ✅ True
}
#+end_src

***** Common Mistake Without `instanceof`

#+begin_src java
Parent p = new Parent(); // ❌ actual object is NOT a Child

Child c = (Child) p; // ❌ Compiles, but throws ClassCastException at runtime
#+end_src

- To avoid this:

*** Arrays.sort() with Comparable

- When you implement Comparable, the class defines how objects of that class should be compared to each other. The sorting logic is embedded within the class itself, and Arrays.sort() uses the compareTo() method of Comparable to sort the array.

How It Works:

- If the class implements Comparable, the objects will be sorted according to the compareTo() method.
- This is a default sorting strategy based on the natural ordering defined in the compareTo() method.

**** Example

#+BEGIN_SRC java
import java.util.*;

class Person implements Comparable<Person> {
    String name;
    int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    // Implementing compareTo to define natural order by age
    @Override
    public int compareTo(Person other) {
        return this.age - other.age;  // Sorting by age (ascending order)
    }

    @Override
    public String toString() {
        return "Name: " + name + ", Age: " + age;
    }
}

public class Demo {
    public static void main(String[] args) {
        Person[] people = {
            new Person("Alice", 30),
            new Person("Bob", 25),
            new Person("Charlie", 35)
        };

        // Sort the array by natural order (age) using Arrays.sort()
        Arrays.sort(people);  // Uses compareTo() method

        // Print the sorted array
        for (Person p : people) {
            System.out.println(p);
        }
    }
}

#+END_SRC

Explanation:

- The Person class implements Comparable<Person>, and the compareTo() method sorts people by age.
- When you call Arrays.sort(people), it uses the compareTo() method to sort the array by age in ascending order.

** Immutable Arrays

In Java, **immutable** types are objects whose state cannot be changed after they are created. This section explains how to create immutable lists in Java, and contrasts them with fixed-size lists like those created using `Arrays.asList()`.

*** 1. `Arrays.asList()` (Fixed-Size, Not Immutable)

The `Arrays.asList()` method creates a list backed by an array. The list is **fixed-size**, meaning that you cannot modify its size (i.e., no adding or removing elements), but you can still modify the elements of the list if the underlying array is mutable.(Introduced in java 1.2)

Example:
#+BEGIN_SRC java
import java.util.*;
List<String> list = Arrays.asList("apple", "banana", "cherry");
list.set(1, "orange");  // This is allowed, list becomes: ["apple", "orange", "cherry"]
System.out.println(list);
#+END_SRC

**** Key Points:
- **Fixed-size List**: You cannot add or remove elements.
- **Mutable Elements**: You can change the elements of the list, because it's backed by an array.

Attempting to add elements will throw an exception:
#+BEGIN_SRC java
list.add("grape");  // Throws UnsupportedOperationException
#+END_SRC

This is because `Arrays.asList()` returns a fixed-size list that does not support resizing.

*** 2. Creating Truly Immutable Collections

In Java, if you want to create a truly immutable collection, you need to use other methods that prevent both the modification of the size of the list and the elements themselves.

**** 2.1 `Collections.unmodifiableList()`

`Collections.unmodifiableList()` wraps an existing list in an immutable wrapper. After wrapping, the list becomes **unmodifiable**, meaning no structural modifications (adding, removing elements) or changes to the list elements are allowed.

Example:
#+BEGIN_SRC java
List<String> list = Arrays.asList("apple", "banana", "cherry");
List<String> immutableList = Collections.unmodifiableList(list);
immutableList.add("grape");  // Throws UnsupportedOperationException
#+END_SRC

**** Key Points:
- **Unmodifiable**: You cannot add, remove, or modify elements.
- **Modifying original list**: The original list (`list`) can still be modified, but `immutableList` remains unmodifiable.

*** 2.2 `List.of()` (Java 9+)

Starting with Java 9, you can create a truly immutable list using `List.of()`. This method creates a list that is **both unmodifiable and immutable**, meaning neither the size nor the elements can be changed after creation.

Example:
#+BEGIN_SRC java
List<String> immutableList = List.of("apple", "banana", "cherry");
immutableList.add("grape");  // Throws UnsupportedOperationException
#+END_SRC

**** Key Points:
- **Immutable**: Once created, the list cannot be modified.
- **No `null` elements allowed**: `List.of()` does not allow `null` elements.
- **Throws exception**: Any modification attempt (e.g., `add`, `set`) will throw `UnsupportedOperationException`.

Invalid example:
#+BEGIN_SRC java
List<String> invalidList = List.of("apple", "banana", null);  // Throws NullPointerException
#+END_SRC

*** 3. Immutable Lists vs. Fixed-Size Lists

Here is a summary comparing **immutable** lists with **fixed-size** lists:

- **Fixed-size List** (e.g., from `Arrays.asList()`):
  - The **size** of the list is fixed (no add/remove operations).
  - The **elements** can be modified if the list is backed by a mutable array.

- **Immutable List** (e.g., from `List.of()` or `Collections.unmodifiableList()`):
  - The **size** is fixed.
  - The **elements** cannot be modified.

*** 4. Summary

- `Arrays.asList()`: Creates a fixed-size list. You cannot resize the list, but you can modify the elements.
- `Collections.unmodifiableList()`: Wraps a list in an unmodifiable wrapper, making it impossible to modify its structure or elements.
- `List.of()`: Creates a truly immutable list. Neither the structure nor the elements can be changed once the list is created.

** Comparator
*** Key Points

- **compare(T o1, T o2)**: This method compares two objects of type T:

** Sorting
*** Collections and Sorting

Collections themselves (such as List, Set, Map, etc.) do not automatically sort the elements they contain. Because there are different kind of sortings. Sorting is generally performed separately, using a method like Collections.sort() or through the use of comparators or comparable objects. Let's break it down:

*** Sorting with Collections.sort()

List : A List is a common collection type that can be sorted. The Collections.sort() method sorts the elements in place (modifies the list itself) in ascending order by default.

#+BEGIN_SRC java
List<Integer> numbers = new ArrayList<>(Arrays.asList(5, 3, 8, 1));
Collections.sort(numbers); // Sorts in ascending order
System.out.println(numbers); // Output: [1, 3, 5, 8]
#+END_SRC

*** Using Comparable (Natural Ordering)

If the objects in the collection implement the Comparable<T> interface, you can sort them using their **natural ordering** (the way they compare to each other by default).

The Comparable interface requires the compareTo() method, which defines how two objects should be compared for sorting.

#+BEGIN_SRC java
import java.util.*;
class Person implements Comparable<Person> {
    String name;
    int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public int compareTo(Person other) {
        return this.age - other.age;  // Sorting by age
    }
    // Override the toString() method to print name and age
    @override
    public String toString() {
        return "Name: " + name + ", Age: " + age;
    }
}

public class Demo{
    public static void main(String[] args){
	List<Person> people = Arrays.asList(
					    new Person("Alice", 30),
					    new Person("Bob", 25),
					    new Person("Charlie", 35)
					    );
	Collections.sort(people);  // Sorts using compareTo()

	for(Person p: people){
	    System.out.println(p);
	}
    }//end main
}
#+END_SRC

#+RESULTS:
: Name: Bob, Age: 25
: Name: Alice, Age: 30
: Name: Charlie, Age: 35

*** Using Comparator (Custom Sorting)

- If you want custom sorting (different from the natural ordering), you can use a Comparator. A comparator can be passed to Collections.sort() or can be used with other sorted collections, like TreeSet or TreeMap.
- Example of using Comparator with Collections.sort():

#+BEGIN_SRC java
import java.util.*;
List<String> words = Arrays.asList("apple", "banana", "cherry");
Collections.sort(words, (a, b) -> b.compareTo(a));  // Sort in reverse order
System.out.println(words);  // Output: [cherry, banana, apple]
#+END_SRC

#+RESULTS:
: [cherry, banana, apple]

*** Set and Map

- **Set**: Collections like HashSet do not maintain any order by default. However, if you use TreeSet, it automatically sorts elements based on their natural ordering or a provided Comparator.
- **Map**: Like Set, HashMap does not maintain any order. However, TreeMap keeps keys sorted, either by natural ordering or a custom Comparator.

*** Summary

- **Lists** can be sorted using Collections.sort(), either by using natural ordering (Comparable) or by providing a custom sorting logic with a Comparator.
- **Sets** like TreeSet and **Maps** like TreeMap maintain elements in a sorted order automatically (by their keys) based on either natural ordering or a custom Comparator.
- Sorting is not automatically done by the collection types themselves; it is explicitly performed using Collections.sort(), Comparable, or Comparator.
*** TreeSet() and TreeMap

- In Java, when you use a TreeSet or a TreeMap, they rely on the ability to compare elements to determine their order.
- If no Comparator is provided and the elements don't implement the Comparable interface, the TreeSet or TreeMap will not know how to order the elements, which will lead to a **runtime exception**.
- Both of these classes call the compareTo() method to sort items for order.

*** Lambda Variables Are Final!

**** The Variables Are Final (Effectively)

In Java, the variables passed to a lambda expression (or anonymous class) must be effectively final. This concept is important to understand, especially when working with lambda expressions and functional interfaces like BiConsumer.

**** What Does "Effectively Final" Mean?

- Effectively final means that a local variable is not actually marked as final, but it behaves like a final variable because its value never changes after it is assigned.
- In other words, a variable is effectively final if, after its initial assignment, you never reassign it to a different value. This ensures that the variable’s value remains constant throughout the lambda expression, which is required for thread-safety and predictability.

Let's break this down with an example:

**** Example: Using BiConsumer with Effectively Final Variables

#+begin_src java
BiConsumer<Integer, Integer> add = (a, b) -> {
    // a and b are passed into the lambda and cannot be reassigned within the lambda body.
    int sum = a + b;  // You can use a and b, but you can't change their values.
    System.out.println("Sum: " + sum);
};
#+end_src

In the above example:

- a and b are the parameters of the BiConsumer's accept() method. They are effectively final because they are not reassigned inside the lambda body.
- You cannot reassign a or b to a new value inside the lambda expression. However, you can read their values and use them to compute other values, such as sum.

**** What Happens If You Try to Reassign?

#+begin_src java
BiConsumer<Integer, Integer> add = (a, b) -> {
    a = 5;  // Compilation error: Cannot assign a value to final variable 'a'
    int sum = a + b;
    System.out.println("Sum: " + sum);
};
#+end_src

This code will not compile because Java is treating a and b as effectively final, and you are trying to reassign a. Since a is a parameter passed to the lambda expression, Java assumes it will not be modified after it's initially set, which is a fundamental rule for lambda expressions (and functional interfaces) in Java.

**** Why Is This the Case?

Java enforces this rule because lambdas may be executed asynchronously (in a different thread), and it’s important that the values of local variables in the lambda expression do not change while the lambda is still being executed. Allowing variables to be reassigned could lead to non-deterministic behavior, where the value of a variable could change while the lambda is still in use. To avoid potential issues, Java requires variables to be effectively final.

**** What You Can Do

Although you can't reassign the parameters a and b, you can use them in calculations or store their values in other variables:

#+begin_src java
BiConsumer<Integer, Integer> add = (a, b) -> {
    int x = a * 2;  // You can use a and b to calculate other variables.
    int y = b * 3;
    int sum = x + y;
    System.out.println("Sum: " + sum);
};
#+end_src

In this case:

- a and b are still effectively final because their values are not reassigned, but you can still perform calculations using their values.
- We’ve introduced x and y as new variables to store the results of the calculations, and you can modify those new variables.

**** What Happens If You Use Non-Final or Mutable Variables?

If you try to modify a local variable (that is neither final nor effectively final) inside a lambda expression, Java will not allow it. However, you can use mutable objects (such as lists, maps, or custom objects) that the lambda may modify because it’s the object state being modified, not the variable reference itself.

For example:

#+begin_src java
BiConsumer<List<String>, String> addToList = (list, item) -> {
    list.add(item);  // Allowed, because we are modifying the state of the object, not the variable reference.
};
#+end_src

In this case:

- list and item are effectively final, meaning you can’t reassign list or item to a different list or string.
- However, you can modify the internal state of list (like adding an item), because you’re working with the object itself, not the reference to the object.

**** Why the "Effectively Final" Rule Is Important

The key reason for this rule is related to thread safety and predictability. By ensuring that local variables used inside lambdas don’t change after they’re assigned, Java guarantees that lambdas behave consistently and are easier to reason about, especially when they are executed in parallel or asynchronously.

**** Recap:

- The parameters of a lambda expression (in this case, a and b in BiConsumer<T, U>) are effectively final, which means they cannot be reassigned once they’ve been initialized.
- You can use the values of a and b, but you cannot reassign them.
- This restriction ensures predictable behavior and thread safety, which is important when using lambdas in concurrent or parallel execution contexts.

*** collectingAndThen
***** Key Points

Collectors.collectingAndThen is a utility method from the Collectors class in the Java Stream API. It allows you to wrap an existing collector with a finishing function that is applied after the collection process has completed. This is useful when you want to perform an additional transformation or action on the result of a collection (e.g., a List, Set, or Map) once it has been fully accumulated.

***** Signature
#+BEGIN_SRC java
public static <T, A, R> Collector<T, A, R> collectingAndThen(
   Collector<? super T, A, R> downstream,
    Function<? super R, ? extends R> finishing
)
#+END_SRC

- downstream: This is the original collector that accumulates elements in a particular manner (e.g., into a List, Set, or Map).
- finishing: This is the finishing function that applies a transformation to the result of the downstream collector once all elements have been collected.

***** How it works:

The method takes an existing collector (downstream) and applies a transformation (finishing) to the result once the collecting operation is done. The final result returned by collectingAndThen will be the result of the transformation applied to the result of the downstream collector.

***** Example with List

#+BEGIN_SRC java
import java.util.*;
import java.util.stream.*;
List<String> strings = Arrays.asList("apple", "banana", "cherry");

// Collect the strings into a List and then make it unmodifiable
List<String> result = strings.stream()
    .collect(Collectors.collectingAndThen(
	Collectors.toList(), // Downstream collector: collect into a List
	Collections::unmodifiableList // Finishing function: make the list unmodifiable
  ));

System.out.println(result);
// result.add("date"); // This would throw UnsupportedOperationException
#+END_SRC

- Collectors.toList() is the downstream collector, which collects the elements into a List.
- Collections::unmodifiableList is the finishing function that wraps the list in an unmodifiable List, preventing any modifications to the collection after it has been created.

***** Example with Map

#+BEGIN_SRC java
import java.util.*;
import java.util.stream.*;
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5);

        Map<Integer, Integer> squaredMap = numbers.stream()
            .collect(Collectors.collectingAndThen(
                Collectors.toMap(
                    num -> num, // Key: the number itself
                    num -> num * num // Value: the square of the number
                ),
                map -> {
                    map.replaceAll((k, v) -> v * 2); // Finishing function: double all the squared values
                    return map;
                }
            ));

        System.out.println(squaredMap); // {1=2, 2=8, 3=18, 4=32, 5=50}
#+END_SRC

- Collectors.toMap() is the downstream collector, which creates a Map from the numbers.
- The finishing function modifies the map by doubling the squared values.

***** Why Use collectingAndThen?

Post-processing: After collecting elements using a standard collector, you can apply a finishing transformation to the result (e.g., making a collection unmodifiable, modifying the values, etc.).
Readability and Convenience: It allows you to combine collection and transformation logic in a readable and functional manner, without having to manually process the result after collection.

***** Key Takeaways:

Collectors.collectingAndThen is useful when you need to apply a transformation or finishing step to the result of a collection operation.
The first argument is the downstream collector that performs the accumulation (e.g., toList(), toMap(), etc.).
The second argument is a finishing function that modifies or processes the result once the collection is complete.

*** groupingBy()

**** Key Points

- The return type of groupingBy() is always Map<K, V>.
- It accepts a [[Function]] which returns the key (K) used for grouping.
- The value in the map is the **collection of elements that share the same key**, typically a List<T>.
- **The key is created or modified, not the value.**
- The groupingBy() method in Java’s Stream API does **NOT** modify the original List<T> or any other collection; it simply groups the elements based on a key, creating a new Map<K, List<T>> where:
  - The keys are the results of the classification function (e.g., categories, ranges, or other properties of the elements).
  - The values are collections (typically List<T>) that hold the elements from the original stream that have the same key.

**** Method Signature

#+begin_src java
public static <T, K> Collector<T, ?, Map<K, List<T>>> groupingBy(
    Function<? super T, ? extends K> classifier)
#+end_src

- **T**: The type of elements in the stream.
- **K**: The type of the key used to group the elements.
- **classifier**: A function that extracts the key for each element, which is used to group them.
- **Returns**: A Map<K, List<T>>, where each key corresponds to a group of elements from the stream.

**** Examples

groupingBy() can be used with a single function to group elements based on a key.

*** groupingByConcurrent

`Collectors.groupingByConcurrent` is a collector in the Java Streams API that allows you to group elements of a stream into a `Map` in a thread-safe, concurrent manner. It is similar to `Collectors.groupingBy`, but designed for parallel processing scenarios where the grouping operation can be done safely in concurrent threads.

**** Syntax**
  #+BEGIN_SRC java
  Map<K, List<T>> result = stream.collect(Collectors.groupingByConcurrent(Function<? super T, ? extends K> classifier));
  #+END_SRC

Where:
- `K` is the type of key that each element is grouped by.
- `T` is the type of the elements in the stream.
- The `classifier` function is used to determine the key (`K`) for each element in the stream.

**** Behavior**
- `groupingByConcurrent` returns a `Map<K, List<T>>`, where the key is the result of applying the classifier function to each element of the stream.
- Unlike `groupingBy`, which may require external synchronization in a multi-threaded environment, `groupingByConcurrent` is designed to handle concurrent updates to the `Map`.
- The collector uses a `ConcurrentMap` (e.g., `ConcurrentHashMap`) for efficient parallel processing and thread safety.

**** Example Usage**

#+BEGIN_SRC java
  import java.util.List;
  import java.util.Map;
  import java.util.stream.Collectors;

          List<String> words = List.of("apple", "banana", "orange", "avocado", "blueberry", "apricot");

          Map<Character, List<String>> groupedByFirstLetter = words.stream()
              .collect(Collectors.groupingByConcurrent(word -> word.charAt(0)));

          groupedByFirstLetter.forEach((key, value) -> {
              System.out.println(key + ": " + value);
          });
#+END_SRC

#+RESULTS:
: a: [apple, avocado, apricot]
: b: [banana, blueberry]
: o: [orange]

**** Explanation of Example**
- The stream of words is grouped by the first character of each word using the `groupingByConcurrent` collector.
- In the result, words starting with the same letter will be grouped together in a list and associated with that letter as the key.

**** Key Points**
- Thread-Safety: `groupingByConcurrent` ensures that grouping operations are thread-safe and can be used in parallel streams.
- Performance: While `groupingByConcurrent` is optimized for concurrency, it is generally slower than `groupingBy` when used in a single-threaded environment. It shines in scenarios where a parallel stream is being used.

**** When to Use**
- You should use `groupingByConcurrent` when you have a stream that is being processed in parallel (e.g., via `.parallel()`), and you need to group elements by a key while ensuring thread safety.

**** reducing() vs map() + reduce()

***** 1. Single Operation vs. Two Operations

- **reducing()**: Combines both mapping and reduction into a single operation. This is more concise and efficient when you need to reduce a specific field of the objects (e.g., summing a field like price).
- **map() + reduce()**: Involves two separate operations. First, the map() function converts the stream elements (e.g., Food objects) to a specific type (e.g., Integer for prices), then reduce() performs the actual reduction.

***** 2. When to Use map()

- **Use map()** when you need to transform the stream before performing reduction or other operations. For example, if you need to apply multiple transformations on the stream elements before reducing them, map() provides more flexibility.
- **Use reducing()** when you need to reduce a single field (e.g., summing prices) as it is simpler and more direct.

*** peek()

***** Non-terminal operation: peek()

peek() is a **non-terminal operation** that allows you to **inspect the elements as they flow through a stream**. It doesn't modify the elements or affect the stream's result. It is mainly used for **debugging** or logging the elements during stream processing.

***** Key Points:

- **Purpose**: To observe or inspect elements of the stream without changing them.
- **Does Not Modify the Stream**: The stream still behaves as it would without peek(), and the stream's final result is unaffected.
- **Used for Debugging**: It's typically used to see what data is in the stream at certain points in the pipeline.

**** How It Works:

The peek() method allows you to perform some action (like printing or logging) on the elements as they are processed by the stream, but it doesn't modify them. It's like looking at the elements **in transit** without stopping them.

----

**** Example:

Imagine you have a stream of numbers, and you want to print each number just before performing some transformation or operation on it:

       .peek(n -> System.out.println("Before doubling: " + n))  // Peek before doubling
       .map(n -> n * 2)  // Double the number
       .peek(n -> System.out.println("After doubling: " + n))  // Peek after doubling
       .forEach(System.out::println);  // Print the final result
#+END_SRC

----

**** Breakdown:

1. The first peek() logs each element **before** it is doubled.
2. The map(n -> n * 2) operation doubles each number.
3. The second peek() logs each element **after** it has been doubled.
4. The forEach() terminal operation prints the final doubled numbers.

----

**** Why Use peek()?

- **Debugging**: It’s useful when you want to inspect the elements at different points in the stream pipeline (e.g., before and after a transformation), especially when debugging complex stream operations.
- **Logging**: You can use peek() to log the data at various points in your stream pipeline to understand how it changes.
- **Non-Modifying**: It allows you to inspect data without changing the actual stream operations.

----

**** Important Notes:

- **Side Effects**: The action inside peek() should generally not modify the elements or affect the stream's operation. It’s mainly for observation, not transformation.
- **Lazy Operation**: Like all stream operations, peek() is lazy, meaning it won’t execute until a terminal operation (like forEach(), collect(), etc.) is invoked.

----

**** When Not to Use peek():

- **Not for Business Logic**: It’s not intended to be used for transforming data (like map() or filter() would). Use those operations if you want to modify the elements.
- **Side-Effects Can Be Dangerous**: If you have side effects inside peek(), like modifying the stream elements or changing external state, it could lead to unexpected behavior. It’s best used for **observing**, not for altering data.

**** What is IntStream?

IntStream is a special type of stream in Java that allows you to work with a list of int values (whole numbers) in a simple and efficient way. It is part of the Streams API introduced in Java 8, which lets you work with data in a functional (non-imperative) way.
**** Why use IntStream?

**** Example:

    Filter out the even numbers.
    Multiply each remaining number by 2.
    Add them all together.

Here’s how you can do that using IntStream:

#+BEGIN_SRC java
import java.util.stream.IntStream;

    .map(n -> n * 2): This multiplies each remaining number by 2.
    .sum(): Finally, this adds up all the numbers.

The output of the above code is 18, because:

    We keep only the odd numbers (1, 3, 5).
    Then, multiply each by 2 (2, 6, 10).

*** reduce()

**** Description:
- Definition: reduce() is a general-purpose reduction operation that accumulates the elements of a stream into a single result using a binary associative operation (combiner). It is a general-purpose method. It works with any data type, primitive, wrapper, Stream<T> etc.

- Parameters:
  - Binary Operator: A function that takes two values and combines them into one.
  - Optionally, you can provide an identity value (the initial value for the reduction), or it can return an Optional result if no identity is provided.

#+BEGIN_SRC java
int sum = numbers.stream().reduce(0, (a, b) -> a + b);
#+END_SRC

- **Terminal operation**: reduce() is a terminal operation in streams, meaning it produces a result or a side-effect.
- **Reduces the stream to a single result**: It combines all elements of the stream into a single value using an accumulator function.
- **Stateful and bounded**: It keeps track of the accumulated result and operates over the entire stream.

reduce() is similar to:

#+BEGIN_SRC java
int sum = 0;
for (int i = 0; i <= 5; i++) {
    sum += i;
}
System.out.println(sum);
#+END_SRC

**** Method Signature:

reduce() is an overloaded method:

1. **Optional reduce(BinaryOperator accumulator)**

   - Takes a BinaryOperator<T>, which is a function that combines two elements of type T into one result of type T.

   #+BEGIN_SRC java
   reduce((a, b) -> a + b); // Implementation 1
   Optional<Integer> r1 = list.stream().reduce((a, b) -> a + b);
   #+END_SRC

2. **U reduce(U identity, BiFunction<U, ? super T, U> accumulator, BinaryOperator combiner)**

   - Takes an identity value and combines it with elements of the stream using the provided functions.

   #+BEGIN_SRC java
   reduce(0, (x, y) -> (x + y)); // Implementation 2

   int summation = list.stream().reduce(0, (x, y) -> (x + y));
   int product = list.stream().reduce(1, (x, y) -> (x * y)); // Notice 1 for multiplication
   #+END_SRC

   - **Explanation**: The identity value (e.g., 0 for summation, 1 for multiplication) is the initial value. The accumulator function takes two arguments and combines them (e.g., addition for sum, multiplication for product). This version does not return an Optional because we are providing an identity value.

**** BinaryOperator<T> and Function<T, T>:

- BinaryOperator<T> extends BiFunction<T, T, T> and is used in the reduce() method to combine two elements of the stream into one.
- It works like a for-loop where the result is accumulated:

#+BEGIN_SRC java
public interface BinaryOperator<T> extends BiFunction<T, T, T>
#+END_SRC

- BinaryOperator takes two values of type T and returns a single value of type T. It is used to accumulate results such as summing values or finding the maximum.

**** How reduce() Works:

The reduce() method combines elements of the stream into a single result by repeatedly applying a binary operator (a function that takes two elements and returns one). It reduces the stream to a single value.

- **reduce(BinaryOperator<T> accumulator)**: Combines two elements of the stream using the provided binary operator.
- **reduce(T identity, BinaryOperator<T> accumulator)**: Takes an identity value and the accumulator function.

** Collectors returning Optional
In Java's Stream API, several `Collector` methods return an `Optional` because the result of the operation might not be present. These methods typically return `Optional.empty()` when the stream is empty or when no result is available for the operation.

*** Collector Methods Returning Optional

1. `Collectors.minBy(Comparator<T> comparator)`
2. `Collectors.maxBy(Comparator<T> comparator)`
3. `Collectors.reducing(BinaryOperator<T> op)` (with no identity)

These methods return an `Optional<T>` because the result of the operation may not be present. For example, if the stream is empty, these methods will return `Optional.empty()`.

*** When Do These Collectors Return `Optional.empty()`?

- `Collectors.minBy` and `Collectors.maxBy` will return `Optional.empty()` if the stream is empty (because there’s no minimum or maximum value to compute).
- `Collectors.reducing` will return `Optional.empty()` if the stream is empty and no identity is provided. If an identity is provided, it will always return a result (even if the stream is empty).

*** Examples

**** 1. Using `Collectors.minBy`

#+BEGIN_SRC java
List<Integer> numbers = Arrays.asList();
Optional<Integer> min = numbers.stream().collect(Collectors.minBy(Integer::compare));
System.out.println(min);  // Output: Optional.empty
#+END_SRC

- Since the list is empty, there's no minimum value, so it returns `Optional.empty()`.

**** 2. Using `Collectors.maxBy`

#+BEGIN_SRC java
List<Integer> numbers = Arrays.asList(5, 10, 15);
Optional<Integer> max = numbers.stream().collect(Collectors.maxBy(Integer::compare));
System.out.println(max.get());  // Output: 15
#+END_SRC

- Here, `max` returns `Optional[15]`, because 15 is the maximum value in the list.

**** 3. Using `Collectors.reducing`

#+BEGIN_SRC java
List<Integer> numbers = Arrays.asList(1, 2, 3, 4, 5);
Optional<Integer> sum = numbers.stream().collect(Collectors.reducing(Integer::sum));
System.out.println(sum.get());  // Output: 15
#+END_SRC

- The sum of the numbers is computed and returned as `Optional[15]`.

**** 4. Empty Stream with `reducing`

#+BEGIN_SRC java
List<Integer> numbers = Arrays.asList();
Optional<Integer> sum = numbers.stream().collect(Collectors.reducing(Integer::sum));
System.out.println(sum);  // Output: Optional.empty
#+END_SRC

- Since the stream is empty, there's no sum to compute, so it returns `Optional.empty()`.

*** Summary

- **`Optional` in Collectors**: Collector methods like `minBy`, `maxBy`, and `reducing` return `Optional.empty()` when there is no result (e.g., for empty streams). This allows safe handling of cases where no value is available.
- **With Identity in `reducing`**: If you provide an identity (e.g., `Collectors.reducing(0, Integer::sum)`), it won't return `Optional.empty()`. The identity ensures a value is always returned, even for empty streams.

*** ExecutorService

ExecutorService is a higher-level replacement for managing threads manually via Thread objects.

https://www.youtube.com/watch?v=6Oo-9Can3H8

**** Key Features of ExecutorService:

- Thread Pooling: It manages a pool of worker threads to execute tasks. This avoids the overhead of creating and destroying threads every time a task is submitted, which can be expensive in terms of time and resources.

- Task Scheduling: It allows you to submit tasks (runnable or callable) for execution and retrieve their results in a manageable way.

- Graceful Shutdown: It provides mechanisms to gracefully shut down the executor, allowing for the proper completion of tasks before the threads are terminated.

**** Core Interface of Executor Framework:

Executor: The basic interface that defines a method execute(Runnable command) to submit tasks.

ExecutorService: Extends Executor and provides more advanced methods for managing tasks, such as submitting Callable tasks, checking if the service is shut down, and shutting it down.

**** Key Methods of ExecutorService:

1. **`submit()`**:
   - The `submit()` method is used to submit tasks to the executor.
   - It can accept both `Runnable` and `Callable` tasks.
   - It returns a `Future` object, which allows you to track the status of the task and retrieve the result (if it's a `Callable`).

   Example:
   #+begin_src java
   Future<?> future = executorService.submit(new RunnableTask());
   #+end_src

2. **`invokeAll()`**:
   - This method accepts a collection of `Callable` tasks and executes them.
   - It blocks until all tasks have completed and returns a list of `Future` objects corresponding to each task.

   Example:
   #+begin_src java
   List<Callable<Integer>> tasks = Arrays.asList(new Task1(), new Task2());
   List<Future<Integer>> results = executorService.invokeAll(tasks);
   #+end_src

3. **`invokeAny()`**:
   - This method also accepts a collection of `Callable` tasks, but it returns the result of the first successfully completed task.
   - If any task throws an exception, it is retried, and the method blocks until at least one task has completed.

   Example:
   #+begin_src java
   List<Callable<Integer>> tasks = Arrays.asList(new Task1(), new Task2());
   Integer result = executorService.invokeAny(tasks);
   #+end_src

4. **`shutdown()`**:
   - This method initiates an orderly shutdown in which previously submitted tasks are executed, but no new tasks will be accepted.
   - It doesn't immediately terminate the executor, but signals that no new tasks should be submitted.

   Example:
   #+begin_src java
   executorService.shutdown();
   #+end_src

5. **`shutdownNow()`**:
   - This method attempts to stop all actively executing tasks, halts the processing of waiting tasks, and returns a list of the tasks that were waiting to be executed.

   Example:
   #+begin_src java
   List<Runnable> pendingTasks = executorService.shutdownNow();
   #+end_src

6. **`isShutdown()` and `isTerminated()`**:
   - `isShutdown()` returns `true` if the executor has been shut down (via `shutdown()` or `shutdownNow()`).
   - `isTerminated()` returns `true` if all tasks have completed following a shutdown.

   Example:
   #+begin_src java
   boolean shutdownStatus = executorService.isShutdown();
   boolean terminationStatus = executorService.isTerminated();
   #+end_src

**** Example Usage of ExecutorService:

1. **Creating and Using ExecutorService with Runnable and Callable**:

   Example code:
   #+begin_src java
   import java.util.concurrent.*;

   public class ExecutorServiceExample {
       public static void main(String[] args) throws InterruptedException, ExecutionException {
           // Create an ExecutorService using a fixed thread pool
           ExecutorService executorService = Executors.newFixedThreadPool(3);

           // Submitting a Runnable task (doesn't return a result)
           Runnable task1 = () -> System.out.println("Task 1 is running on thread: " + Thread.currentThread().getName());
           executorService.submit(task1);

           // Submitting a Callable task (returns a result)
           Callable<Integer> task2 = () -> {
               System.out.println("Task 2 is running on thread: " + Thread.currentThread().getName());
               return 42; // Return a result
           };
           Future<Integer> future = executorService.submit(task2);

           // Getting the result from the Callable task
           Integer result = future.get();  // This will block until the task completes
           System.out.println("Result of task2: " + result);

           // Shutdown the ExecutorService gracefully
           executorService.shutdown();
       }
   }

*** InterThread Communication: Producer and Consumer
https://youtu.be/eQ9aP19ytaM?t=3276

When there is a common object, Producer needs to create data so Consumer can consume. If there is no data Consumer can not consume. If there is data already Producer can not produce, it needs to wait Consumer to consume the data.

To organize this, developers create wait and notify process. You create a common object, you make producer to wait untill data is consumed.

#+BEGIN_SRC java
class SharedBuffer{

private int data;
private boolean available = false;

public synchronized void produce(int value) throws InterruptedException{
while(available){
    wait();
}//end while
data = value;
available=true;
System.out.println("Produced: " + data);
notify();//notify the other thread.
}//end Method

public synchronized void consume() throws InterruptedException{
while(!available){
    wait();
System.out.println("Consumed: " + data);
available = false;
notify();//notify the other thread.
}//end while
}//end consume
}//end class

class Producer extends Thread{
    private SharedBuffer sharedBuffer;

    //Constructor
    public Producer(SharedBuffer sharedBuffer){
    this.sharedBuffer = sharedBuffer;
    }

    //because it exteds thread we need to override run()

    @Override
    public void run(){
	for(int i =0; i <= 5; i++){
	    try{
	    sharedBuffer.produce(5);
	    }catch(InterruptedException e){
		e.printStackTrace();
	    }
	    }
    }
}


class Consumer extends Thread{
    private SharedBuffer sharedBuffer;

    public Consumer(SharedBuffer sharedBuffer){
	this.sharedBuffer = sharedBuffer;
    }

    //override the run method because extending Thread
    @Override
    public void run(){
	for(int i =0; i <=5; i++){
	    try{
	    sharedBuffer.consume();
	    Thread.sleep(1000);
	    }catch(InterruptedException e){
		e.printStackTrace();
	    }
	}
    }

}

Asysnchronous programming is not related to concurrent programming.

** Helper Classes or Utility Classes

In Java, a **helper class** (also called a **utility class**) is a class that contains **static methods** and sometimes **static variables**, which are used to perform common, reusable operations across an application. These classes are **not meant to be instantiated**.

**** Characteristics of a Helper Class:

- Methods are usually `static`
- Designed for code reuse and separation of concerns
- Not intended to represent real-world objects (unlike model classes)
- Often final (optional), with a private constructor to prevent instantiation

**** Example:

#+BEGIN_SRC java
public final class MathHelper {

    // Private constructor prevents instantiation
    private MathHelper() {}

    public static int add(int a, int b) {
        return a + b;
    }

    public static int factorial(int n) {
        if (n <= 1) return 1;
        return n * factorial(n - 1);
    }
}
#+END_SRC java

**** Usage:

#+BEGIN_SRC java
int sum = MathHelper.add(5, 10);
int fact = MathHelper.factorial(5);
#+END_SRC java

**** Common Examples in Java:

- `java.util.Collections` – utility methods for working with collections
- `java.util.Arrays` – methods for array manipulation
- `java.lang.Math` – mathematical operations

**** Why Use Helper Classes?

- Improve code organization
- Promote code reuse
- Simplify testing (since methods are stateless and predictable)

** FileReader and FileWriter
FileReader and FileWriter are Java classes used to read and write **text files**.
They work with **characters** (not bytes).
*** *FileReader – Reading text files*
- Used to read characters from a file.
- Reads data character by character.
- Example:

#+BEGIN_SRC java
import java.io.FileReader;
import java.io.IOException;

public class ReadExample {
    public static void main(String[] args) {
        try {
            FileReader reader = new FileReader("example.txt");
            int ch;
            while ((ch = reader.read()) != -1) { // read() returns -1 at end of file
                System.out.print((char) ch);
            }
            reader.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
#+END_SRC

**What happens:**
It opens "example.txt", reads one character at a time, prints it, and then closes the file.

*** FileWriter – Writing text files*
- Used to write characters to a file.
- Writes data character by character.
- Example:

        } catch (IOException e) {

    }
}
#+END_SRC

** BufferedReader and BufferedWriter in Java
BufferedReader and BufferedWriter are used to **read and write text files more efficiently** than FileReader and FileWriter.

They use a **buffer** (a small block of memory) to temporarily store data, so instead of reading or writing one character at a time, they handle larger chunks — making them **faster**.

*** BufferedReader – Reading text efficiently*
- Wraps around a FileReader.
- Reads large chunks of text at once.
- Provides methods like `readLine()` to easily read whole lines.

#+BEGIN_SRC java
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class BufferedReadExample {
    public static void main(String[] args) {
        try {
            BufferedReader reader = new BufferedReader(new FileReader("example.txt"));
            String line;
            while ((line = reader.readLine()) != null) { // reads one line at a time
                System.out.println(line);
            }
            reader.close();
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
#+END_SRC

**What happens:**
It opens "example.txt", reads one line at a time, and prints each line until the end of the file.

---

*** BufferedWriter – Writing text efficiently*
- Wraps around a FileWriter.
- Writes large chunks of text at once.
- Has a `newLine()` method to easily insert line breaks.

#+BEGIN_SRC java
import java.io.BufferedWriter;
import java.io.FileWriter;

            writer.write("This is faster than FileWriter.");
            writer.close();
            System.out.println("Data written successfully.");
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}
#+END_SRC

**What happens:**
It writes two lines of text to "example.txt", using a buffer to improve speed.

|------------------+---------------------------+--------------+---------------------------|
| BufferedReader   | Reads text efficiently    | Characters   | `readLine()` for lines    |
| BufferedWriter   | Writes text efficiently   | Characters   | `newLine()` for new lines |

* Difference Between return and break in Java

** return
- Exits the *entire method* immediately.
- If used inside the `main()` method, it ends the program.
- It does *not* return to the `main()` method from another method — it just exits the current method entirely.
- Often used to end a method early when a certain condition is met.

  #+BEGIN_SRC java
  public static void main(String[] args) {
      for (int i = 0; i < 10; i++) {
          if (i == 5) {
              return; // Exits the main method, program ends here
          }
          System.out.println(i);
      }
      System.out.println("This will not print.");
  }
  #+END_SRC

** break
- Exits *only the current loop* (for, while, or do-while).
- The rest of the code after the loop continues to run.
- Useful when you want to stop looping after a condition is met but keep executing the method.

  #+BEGIN_SRC java
  public static void main(String[] args) {
      for (int i = 0; i < 10; i++) {
          if (i == 5) {
              break; // Exits the loop, but not the method
          }
          System.out.println(i);
      }
      System.out.println("This will print after the loop.");
  }
  #+END_SRC

** Summary
| Statement | Effect                         |
|-----------+--------------------------------|
| return    | Exits the entire method        |
| break     | Exits only the current loop    |

** Maven Project Structure: main vs test

In a Maven project, code and resources are separated by purpose:

- `src/main`
  - `src/main/java`: Contains your production Java source code.
  - `src/main/resources`: Non-Java files used by your application (e.g., config files, XMLs).
- `src/test`
  - `src/test/java`: Contains test classes (usually using JUnit, TestNG).
  - `src/test/resources`: Resources needed during test execution (e.g., test data).

*** Key Differences

| Aspect       | src/main                       | src/test                          |
|--------------+--------------------------------+-----------------------------------|
| Purpose      | Production application code    | Test code                         |
| Compilation  | Included in final build (e.g., JAR) | Compiled only during test phase |
| Dependencies | Regular dependencies           | Scoped with `<scope>test</scope>` |

This separation improves project organization, maintainability, and ensures only necessary code and libraries are packaged with your final artifact.
